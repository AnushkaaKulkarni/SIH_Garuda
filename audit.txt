GARUDA EXISTING PROJECT AUDIT
Audit date: 2026-10-13 (Asia/Calcutta)
Scope: source inspection of the current workspace. No application source changes made for this audit.

1. EXECUTIVE SUMMARY

Overall readiness: PARTIAL; suitable as a locally run training-simulator prototype, not yet evidenced as a secure, persistent, multi-user unit training product. A substantive Three.js live simulation, event-based trainee workflow, deterministic seeded threat generator, scoring, browser-local session history, event replay, and phone-to-laptop camera pairing exist. The project also has actual WebXR entry logic and a dedicated live phone scene. Authentication, database-backed unit workflows, real adaptive assignment, several admin analytics, and sensor degradation are absent or represented by static UI. There is no evidence of deployment hardening or physical-device validation.

Strongest completed capabilities: seeded multi-threat simulations with varied movement; ground-truth classification and computed scoring; event/session storage and recorded-session AAR; live desktop scene rendered to the paired phone; source-level separate-eye rendering via Three.js StereoEffect on the phone scene; and voice command parsing wired to mission actions.

Most important gaps and risks: client-side role selection is not authentication or authorization; phone pairing and snapshots live in a process-local Map and are not durable or multi-instance safe; pairing-code-only close and scene publication do not authenticate the controller; scoring's detection clock starts at mission start rather than each threat's detectability; non-Himalayan priority/response evaluation is narrower than a robust explicit decision tree; training history is browser-local and not shared across trainees or units; adaptive/admin statistics are hardcoded; and phone stereo, tracking, orientation behavior, reconnect, and headset behavior remain unverified on hardware.

This is a source audit, not proof of complete real-world operation. No application files other than this audit report were intentionally written. No physical phone/headset test, deployed-network test, database test, or intrusive security test was performed.

Status definitions: IMPLEMENTED = concrete source behavior present; PARTIAL = meaningful implementation with material gaps; MISSING = no meaningful implementation located; UNVERIFIED = source cannot establish runtime/device behavior.

3. ARCHITECTURE AND DATA FLOW

Framework and entry points:
- `frontend/app/*/page.tsx` contains Next App Router routes. Main flows are `/soldier/training`, `/soldier/training/[scenario]/briefing`, `/soldier/training/[scenario]/simulation`, `/soldier/aar/[session]`, `/phone-test`, and admin routes.
- `frontend/components/soldier/training-experience.tsx` exposes training library and briefing; `training-live-simulation.tsx` owns the actual mission UI/state; `training-simulation-scene.tsx` owns the R3F scene; `training-aar.tsx` reads saved sessions and renders analysis/replay.
- `frontend/lib/types.ts` contains static scenario and trainee catalogs. `frontend/lib/training-session.ts` defines session/event types, generator, scoring, metrics, What-If and browser persistence. `frontend/lib/vr-commands.ts` parses voice intents.
- Renderer is `Canvas` from `@react-three/fiber`, Three.js PerspectiveCamera, OrbitControls, custom `Drone`/`Terrain`; `TrainingXRLayer` connects XRStore. The dedicated phone route adds `MobileStereoRenderer` (Three.js StereoEffect) and resize handler.

Simulator data flow:
1. Scenario metadata comes from static `scenarios` in `lib/types.ts`; URL selects scenario and desktop/VR-ready mode.
2. `LiveSimulation` chooses initial difficulty, creates session ID/seed, then generates threats. Himalayan Shield uses `generateHimalayanThreats`; other scenarios use an inline seeded generic generator.
3. `TrainingSimulationScene` receives contacts derived from threat definitions and spawn events. `Drone` animates visible contacts. Selecting a spawned contact records `DRONE_DETECTED`; classification, priority and response functions append corresponding events with ground-truth comparisons.
4. `finishMission` creates missed events for never-detected threats, appends mission completion, calls `calculateSessionScore`, builds a v4 `TrainingSession`, then `saveTrainingSession` writes full session and history to browser localStorage/sessionStorage.
5. AAR route reads a session by ID from that same browser storage; `getSessionMetrics`, `getWhatIfOpportunity` and `RecordedReplay` derive display data from the stored definitions/events.

Authoritative and duplicated/transient state:
- Laptop `LiveSimulation` state is authoritative for mission, threat truth, events and score. This is explicit in phone panel messaging and flow.
- `PhoneControlPanel` polls API orientation and stores latest frame in module-local `lib/phone-control.ts`; the same API route keeps a process-local phone session/snapshot Map. Phone browser separately keeps latest sensor frame locally and posts to API.
- Scenario definitions are static catalog plus per-run generated arrays. Admin visual edits do not mutate catalog. Admin analytics and trainee records are independent hardcoded values, not aggregates of stored sessions.
- UI event state and `eventLog` ref are maintained together; session storage persists only at completion. Interrupted sessions are not durable/recoverable from backend.

5. SCORING AND EVALUATION AUDIT

Implementation: `frontend/lib/training-session.ts`, `calculateSessionScore`, uses a `safeThreatCount = max(threat count, 1)`. For each threat with a detection, detection points are `(30 / n) * max(0, 1 - (detection.elapsedMs / window) * 0.35)`. Windows are Easy 15,000 ms, Medium 10,000 ms, Hard 8,000 ms, Expert 6,000 ms. Correct latest classification yields `30/n`; correct latest priority yields `20/n`. Under active `event-performance-v3`, response points equal 20 times correct response count divided by response event count, or zero if no responses. Total is rounded and clamped to 0..100. `finishMission` currently selects v3. `event-performance-v1` has a limited penalty formula; v2/v3 no negative penalties; earlier versions remain supported.

Ground truth is `SessionThreat.expectedClassification` and `.priority`; event records include expected/actual classification/priority/action. `responseIsCorrect` maps Hostile to “Escalate alert”, Unknown to “Track priority threat”, Friendly to “Continue monitoring”. Wrong decisions earn no category points (except v1 penalty rule). Missed events are created at mission finish for every threat without a detection.

Timing limitation: event elapsed time is `timestamp - missionStartedAt`. It is not elapsed time since the contact became visible/detectable. Threat definitions have `spawnTimeMs`, but scoring does not subtract it. Consequently later-spawned threats are structurally disadvantaged by the same absolute detection window; missed detections are not independently penalized in v3 beyond lost category opportunity. `getSessionMetrics` similarly compares mission-relative detection elapsedMs with the difficulty window.

Priority evaluation: `getHimalayanThreatAssessment` uses fixed protected zones, waypoint proximity, path speed and expected classification to derive direction/status/priority/time-to-zone. In non-Himalayan runs, generated `priority` largely follows classification; the simulator's assessment display does not model a complete doctrinal decision tree. Response correctness ignores whether earlier workflow steps were timely or response had downstream effect.

Repeatability/explainability: seed, threat set, event details, score rule and score breakdown persist in each session. Existing tests assert high-vs-low scoring, v3 response averaging, What-If improvements and a fixed-seed generator. No tests cover scoring timestamps against spawn/detectability, all legacy score versions, or live end-to-end session persistence.

6. AAR, PERSISTENCE, AND ANALYTICS AUDIT

`saveTrainingSession` stores the full v4 session under `garuda-training-session:<id>` in localStorage, last session JSON in sessionStorage, and an index under `garuda-training-sessions`. `readTrainingSession` validates a subset of fields and AAR loads from localStorage. Thus session retrieval after reload is possible in same browser profile if origin/storage remains. This is client/browser persistence only, not server-side durable storage.

AAR reads event history, computes metrics, renders threat-by-threat outcomes, static-rule-derived strengths/weaknesses/recommendations and recorded event timeline. Replay uses the recorded threats and events to reconstruct contact positions at playback time. What-If applies one event edit to copied event data, recalculates score, and animates a hypothetical event timeline; it does not re-simulate causes and consequences. No export/download function located.

Individual trends are based on local history index and can be displayed for the current browser only. No account identity is attached. Admin analytics in `components/admin/admin-experience.tsx` uses fixed arrays and literals; trainee records in `lib/types.ts` are static. No unit aggregation, comparisons from actual sessions, or measured improvement across users. `training-experience.tsx` recommendations are also fixed scenario IDs/percentages, not derived from a trainee's recent six sessions despite UI copy.

7. DIFFICULTY AND RANDOMIZATION AUDIT

Difficulty changes several concrete generator parameters. For non-Himalayan scenarios: count scales 0.75/1/1.2/1.4; speed scales 0.65/0.85/1.1/1.35; spawn interval 4200/3000/2000/1000 ms; unknown-class chance 0.16/0.27/0.36/0.44; hostile chance 0.35/0.36/0.38/0.4; signal error rate 0/0.12/0.24/0.4. Himalayan generator uses count 5/6/7/8 and difficulty-specific spawn spacing plus seeded route jitter/classification. Score windows also shorten by difficulty.

Randomness: `createScenarioSeed` uses `crypto.getRandomValues` where available and fallback Math.random; `createSeededRandom` (Mulberry32-style) supplies reproducible threat parameters. Each run saves the seed. Reproducibility is limited to the current generator implementation and does not guarantee deterministic rendering, browser timing, or persisted event replay compatibility across future generator versions. No seed selection control, scenario-validity check, adaptive feedback loop or performance-based parameter selection found.

Instructor control: `ScenarioManagement` modal can change local form fields and shows “saved” message but does not save a scenario or connect it to `scenarios` or `LiveSimulation`. Difficulty is trainee-selectable in live run. No instructor assignment/configuration backend.

8. DESKTOP, MOBILE, AND VR AUDIT

Desktop: R3F Canvas, OrbitControls, keyboard W/A/S/D camera translation, optional voice movement, binocular FOV, scene fullscreen via Fullscreen API; errors handled for fullscreen. Desktop route omits phone pairing component.

Phone pairing: on laptop, PhoneControlPanel creates code with `POST action=create`; phone `/phone-test?pair=...` requests sensor permissions, validates secure context, POSTs connect, sends normalized DeviceOrientation readings at ~34 ms intervals. API validates finite values and rejects updates under 20 ms. Laptop polls latest frame and enables phone CameraRig separately from mouse OrbitControls. Laptop publishes selected scene state every 500 ms; phone polls and renders it as `TrainingSimulationScene` with phone control and mobile optimization. Phone scene snapshot is not a second simulator and contains contacts/environment subset.

Stereo: `phone-test/page.tsx` sets `mobileStereo`; `MobileStereoRenderer` instantiates `StereoEffect`, eye separation 0.064, and calls effect.render on the same live scene/camera; the normal R3F render is supplanted by positive-priority useFrame callback. `StereoEffect` is imported from Three.js addons with installed declared Three version 0.186.1. This is an actual stereo implementation in code, not two CSS copies. Physical optics, correct visual appearance, frame rate and viewport behavior remain UNVERIFIED.

Landscape and sizing: phone start requests fullscreen then calls orientation lock if available; promise rejection becomes a manual rotate instruction. ResizeObserver, window resize and orientationchange update renderer size and camera aspect. This is source-confirmed but browser APIs, viewport/resolution behavior and lock support vary by device.

Tracking/recenter: sensorQuaternion maps alpha/beta/gamma and screen angle; CameraRig captures neutral quaternion and camera base when phone control/recenter key changes; render loop computes relative orientation and slerps with ~0.11s time constant. No yaw unwrap code; quaternion composition should avoid scalar angle subtraction jumps but device-coordinate correctness is hardware/browser-specific. Frame-loop temporary THREE objects are created. No mono/stereo debug control found.

Disconnect: 8-second phone controller lease, 10-minute session TTL, stale-frame and stale-scene checks; phone sensor POST failure stops local control and displays link error. Pairing state is in process memory and lacks automatic restoration after server restart or multi-instance routing. Tunnel expiration and reconnect behavior not tested.

Physical-device/headset tests required: actual left/right eye scene differentiation and alignment; landscape lock accepted/rejected/manual fallback; safe-area/viewport resize after multiple rotations; orientation coordinate direction in landscape; Recenter after yaw wrap and pitch/roll rotations; slow and quick tracking lag; mobile GPU/thermal/frame rate; sensor permission denial/recovery; phone-to-laptop latency/disconnect/re-pair; WebXR headset entry/exit and comfort/performance.

9. SECURITY, RELIABILITY, AND PERFORMANCE RISKS

MEDIUM — No real authentication/authorization. `components/auth/auth-form.tsx` only stores a role in localStorage and routes; page/API authorization checks are not present. Any visitor can directly navigate to admin routes and the interface must not be treated as protecting real unit/personnel data.

MEDIUM — Pairing code is the only access handle for most API actions. `app/api/phone-control/route.ts`: GET exposes frame and live scene to anyone with code; `close` deletes pairing based only on code; `publish-scene` checks active phone lease but not controller ID. A code holder can observe/close a session or overwrite snapshot. Codes are randomly generated (12 symbols from 32-character alphabet, 60 bits), temporary, and UI says keep private; no rate limit or authenticated owner check exists.

MEDIUM — Pairing storage is process-local `globalThis` Map. Restart loses pairings; serverless/multiple instances can disagree about phone and laptop state. Deployment with separate/ephemeral workers risks routine connection failures. No persistence or shared cache is configured in inspected source.

MEDIUM — No backend session persistence/user ownership. localStorage can be cleared, is browser-specific, and has no authorization boundary. This blocks reliable unit reports and poses data integrity risks for training history.

MEDIUM — Detection score timing does not account for threat spawn/detectability. This can make performance comparisons unfair when threats spawn at different times; scoring formula is concrete in `calculateSessionScore`.
